## 🏗️ Architecture Overview

### Core Innovation: RFC-Compliant Priority Scoring

This backend implements a **Gmail Priority Inbox-inspired email scoring system** using RFC-compliant feature extraction and weighted linear models. The system analyzes 22 email features to produce a 0-100 priority score with full explainability.

### Priority Score Categories

- **🔴 Urgent (≥90)**: Immediate attention required
- **🟠 Important (70-89)**: High priority, respond today
- **🟢 Normal (50-69)**: Standard emails
- **⚫ Low (30-49)**: Optional, low priority
- **Spam (<30)**: Likely noise, archive/delete

Newsletters (RFC 2369/2919), auto-generated emails (RFC 3834), and OTPs (RFC 6238) are automatically scored as low priority.

### Scoring Pipeline

```
Email → Feature Extraction → Priority Scoring → Database Cache → API Response → TUI Display
         (22 features)        (weighted model)    (ai_cache)      (JSON)       (🔴🟠🟢⚫)
```

**5-Phase Scoring Algorithm** (`src/core/features/PriorityScorer.ts`):
1. **Negative signals**: Newsletter (-30), auto-generated (-20), OTP (-35)
2. **Positive signals**: Relationship (+30), VIP sender (+15), questions (+20), deadlines (+15-40)
3. **Intent modifiers**: Confirmation requests (+10), action requests (+5), informational (-5)
4. **Special cases**: Calendar invites (override to 85), security alerts (override to 95)
5. **Clamp & categorize**: Normalize to 0-100, assign category

## 🗄️ Database Schema

### SQLite with FTS5 Full-Text Search

```sql
-- Core email storage (24 columns)
emails:
  - id (PK), thread_id, message_id (UNIQUE)
  - subject, sender_email, sender_name, recipient_emails (JSON)
  - date (ISO), body_text, body_html, snippet
  - is_read, is_starred, is_important (BOOL→INT for SQLite)
  - folder, labels (JSON)
  - created_at, updated_at

-- AI/ML feature cache (9 columns)
ai_cache:
  - email_id (PK, FK to emails.id)
  - priority_score (0-100), priority_category (urgent/important/normal/low/spam)
  - priority_reason (explainability text)
  - suggested_action, quick_replies (JSON), draft_suggestions (JSON)
  - sender_profile (JSON)
  - created_at, updated_at

-- Full-text search (FTS5 virtual table)
emails_fts:
  - subject, sender_name, sender_email, body_text, snippet
  - content='emails', content_rowid='rowid'

-- Auto-extracted contacts (7 columns)
contacts:
  - email (PK), name, domain
  - first_seen, last_seen, email_count
```

**Performance Features**:
- WAL mode for concurrent reads/writes
- Strategic indexes on date (DESC), sender, read status, thread_id
- FTS5 for semantic search with LIKE fallback

**Critical Pattern**: SQLite requires integers for booleans
```typescript
// ✅ CORRECT
stmt.run(starred ? 1 : 0, id);

// ❌ WRONG - will throw TypeError
stmt.run(starred, id);
```

## 🌐 HTTP API Endpoints

The API server runs on `http://localhost:5178` and exposes the following endpoints:

### Health & Stats
- `GET /health` - Server health check
- `GET /stats` - Database statistics (email count, unread, contacts)

### Email Operations
- `GET /emails` - List emails with priority scores
- `GET /emails/:id` - Get single email details
- `POST /compose` - Send new email
- `POST /reply` - Reply to email
- `PATCH /emails/:id` - Update email (read, starred, etc.)
- `DELETE /emails/:id` - Delete email

### Priority Scoring (NEW - Week 3)
- `POST /emails/score` - Score single email with explainability
- `POST /emails/score/batch` - Parallel batch scoring (10-50 concurrent)
- `POST /emails/rescore` - Rescore unprioritized emails

### IMAP Sync
- `POST /sync` - Trigger email sync from IMAP server
  - **Uses RFC-based scoring** (not heuristic)
  - Automatically populates `ai_cache` table
  - Powers the Go TUI priority indicators

### AI Features (Optional - Deep Infra/OpenAI-compatible API)
- `POST /ai/quick-replies` - Generate quick replies
- `POST /ai/summarize` - Generate summary
- `POST /ai/draft-suggest` - Generate draft suggestions
- `POST /ai/priority-explain` - AI-assisted explainability (optional)
- `POST /ai/prioritize-all` - Batch AI prioritization (legacy)

**Note**: AI endpoints fall back to heuristic scoring if `DEEPINFRA_API_KEY` is not set.

## 🔧 Development Patterns

### Singleton Pattern (Critical)

All core managers use the singleton pattern:

```typescript
// ✅ CORRECT - use getInstance()
const db = DatabaseManager.getInstance();
const ai = AIManager.getInstance();
const smtp = SMTPManager.getInstance();
const extractor = FeatureExtractor.getInstance();
const scorer = PriorityScorer.getInstance();

// ❌ WRONG - creates multiple instances, breaks caching
const db = new DatabaseManager();
```

### Feature Extraction Flow

When scoring emails:

```typescript
// 1. Extract features (22 features from email)
const features = await FeatureExtractor.getInstance().extractFeatures(email);

// 2. Score with weighted linear model
const result = PriorityScorer.getInstance().calculatePriority(features);
// Returns: { score, category, reasoning, featureWeights, confidence }

// 3. Cache in database
await db.upsertAICache(email.id, result);
```

### Error Handling Strategy

- **Database Layer**: Try/catch with fallback queries, graceful degradation
- **AI Layer**: Heuristic fallback when API unavailable, cached results
- **Network Layer**: Connection status tracking, retry logic
- **API Layer**: HTTP status codes, detailed error messages

## 🧪 Testing Patterns

### Test-Driven Development

The scoring system was built test-first with comprehensive coverage:

```bash
# Run all 111 tests
npm test

# Watch mode for TDD
npm run test:watch

# Interactive UI
npm run test:ui
```

### Key Testing Principles

1. **Neutral Baselines**: Use `0` (not `0.5`) for truly neutral test fixtures
2. **Boundary Testing**: Test category edges (30, 50, 70, 90 scores)
3. **Pattern Matching**: More robust than exact string assertions for reasoning
4. **Explicit Types**: Prevent TypeScript `any[]` inference errors
5. **Feature Isolation**: Test each gate/analyzer/scorer independently

### Example Test Structure

```typescript
describe('PriorityScorer', () => {
  it('should score newsletter as low priority', () => {
    const features: FeatureVector = {
      isNewsletter: true,
      isAutoGenerated: false,
      // ... 20 more features
    };
    const result = scorer.calculatePriority(features);
    expect(result.score).toBeLessThan(50);
    expect(result.category).toBe('low');
    expect(result.reasoning).toContain('newsletter');
  });
});
```

## 🔀 Working with the Go TUI Frontend

### API Integration Points

The Go TUI (`../tui/`) calls these backend endpoints:

1. **Initial Load**: `GET /emails` - Fetch emails with cached priorities
2. **Sync**: `POST /sync` - Trigger IMAP sync + automatic scoring
3. **Read Email**: `GET /emails/:id` - Get full email details
4. **Send Email**: `POST /compose` or `POST /reply`
5. **Update Status**: `PATCH /emails/:id` - Mark read/starred

### Priority Score Flow

```
User syncs emails → TUI calls POST /sync → Backend:
  1. Fetches emails via IMAP
  2. Parses with mailparser
  3. Extracts 22 features per email
  4. Scores with weighted model
  5. Caches in ai_cache table
  6. Returns email list with scores

→ TUI receives scores → Displays priority indicators 🔴🟠🟢⚫
```

### Coordinated Changes

When modifying API contracts:

1. **Update backend**: `src/agent/server.ts`
2. **Update TUI client**: `../tui/internal/data/client.go`
3. **Test integration**: Run `./start.sh` from repo root, verify in TUI
4. **Document breaking changes** in commit messages
5. **Single commit** covers both backend and TUI changes (monorepo advantage)

## 🔑 Key Learnings & Anti-Patterns

### Architecture Decisions

✅ **DO**:
- Use RFC-compliant detection (List-Unsubscribe, Auto-Submitted headers)
- Implement explainability (return reasoning with every score)
- Cache aggressively (ai_cache table prevents re-scoring)
- Use weighted linear models (simple, interpretable, effective)
- Singleton pattern for managers (maintains state, prevents duplication)

❌ **DON'T**:
- Use heuristics without RFC fallback
- Skip explainability (users need to understand scores)
- Score emails without caching (API performance degrades)
- Use complex ML models without interpretability
- Create multiple DatabaseManager instances (breaks connection pool)

### TypeScript Patterns

```typescript
// ✅ CORRECT: Explicit types prevent inference errors
const features: FeatureVector = { ... };
const result: PriorityResult = scorer.calculatePriority(features);

// ✅ CORRECT: Use prepared statements for SQL
const stmt = db.prepare('SELECT * FROM emails WHERE id = ?');
stmt.get(id);

// ❌ WRONG: String concatenation vulnerable to injection
db.exec(`SELECT * FROM emails WHERE id = ${id}`);
```

### Common Issues

**"Emails not loading"**
→ Check: `database.ts:30-40` (schema init), `.env` file (IMAP credentials), `imap.ts:connect()` (TLS/auth)

**"Priority scores not showing in TUI"**
→ Check: `POST /sync` endpoint uses `FeatureExtractor` + `PriorityScorer` (not old heuristic `AIManager.prioritizeEmail()`)

**"SQLite TypeError"**
→ Check: Convert booleans to integers (`starred ? 1 : 0`)

**"Tests failing"**
→ Check: Use neutral baselines (`0` not `0.5`), explicit types, pattern matching

## 🎓 RFC Standards Reference

This project implements the following RFC standards:

- **RFC 2369** - List-Unsubscribe header (newsletter detection)
- **RFC 2919** - List-Id header (mailing list identification)
- **RFC 8058** - One-Click Unsubscribe (HTTPS unsubscribe links)
- **RFC 3834** - Auto-Submitted header (automated messages)
- **RFC 5545** - iCalendar format (calendar invite parsing)
- **RFC 6238** - TOTP algorithm (OTP code detection)

These standards provide deterministic, accurate classification that improves scoring accuracy compared to heuristic-only approaches.
