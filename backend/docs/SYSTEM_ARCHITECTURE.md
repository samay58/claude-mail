## 1. Executive Summary

### What This System Does

Claude Mail is an **RFC-compliant email prioritization engine** that analyzes incoming emails and assigns priority scores from 0-100. The system was inspired by Gmail's Priority Inbox research paper but implements a deterministic, explainable approach using RFC standards rather than opaque machine learning models.

### Key Innovation

Instead of training ML models on user behavior (which requires large datasets and produces unexplainable results), this system uses:

1. **RFC Standards Detection**: Deterministic rules based on email standards (RFC 2369/2919 for newsletters, RFC 3834 for auto-generated, RFC 5545 for calendar invites)
2. **Weighted Linear Scoring**: A transparent 5-phase scoring algorithm where every score has explainable reasoning
3. **Relationship History Analysis**: 6-month lookback with multiple weighted components

### Core Metrics

| Metric | Value |
|--------|-------|
| Features Extracted | 22 per email |
| Scoring Phases | 5 |
| Test Coverage | 111 tests, 100% passing |
| RFC Standards Implemented | 5 |
| Priority Categories | 5 (urgent, important, normal, low, spam) |

### Design Principles

1. **Explainability First**: Every priority score comes with human-readable reasoning
2. **RFC Compliance**: Use email standards rather than heuristics where possible
3. **Deterministic Gates**: Binary classifiers that don't require training data
4. **Singleton Pattern**: All managers use singleton for connection pooling
5. **Caching**: Scores cached in database to avoid recalculation

## 4. Feature Extraction System

### Complete Feature Vector (22 Fields)

```typescript
interface MessageFeatures {
  email_id: string;

  // ═══════════════════════════════════════════════════════════════
  // STAGE 1: RFC DETERMINISTIC GATES (8 fields)
  // These use email standards for high-accuracy binary detection
  // ═══════════════════════════════════════════════════════════════

  is_newsletter: 0|1;              // RFC 2369/2919 List-* headers
  is_auto_generated: 0|1;          // RFC 3834 Auto-Submitted header
  has_list_unsubscribe: 0|1;       // RFC 2369 one-click unsubscribe
  has_list_id: 0|1;                // RFC 2919 mailing list identifier
  has_auto_submitted: 0|1;         // RFC 3834 auto-submitted presence
  has_calendar: 0|1;               // RFC 5545 text/calendar MIME type
  calendar_start_epoch: number|null;  // Parsed event start time
  otp_detected: 0|1;               // Verification/2FA code detected
  otp_age_minutes: number|null;    // Time since OTP received

  // ═══════════════════════════════════════════════════════════════
  // STAGE 2: RELATIONSHIP FEATURES (5 fields)
  // Based on 6-month interaction history with sender
  // ═══════════════════════════════════════════════════════════════

  relationship_score: number;      // 0.0-1.0 composite score
  is_vip_sender: 0|1;              // User-flagged VIP
  reply_count_from_user: number;   // How often user replies to sender
  reply_count_to_user: number;     // How often sender replies to user
  last_interaction_epoch: number|null;  // Timestamp of last contact

  // ═══════════════════════════════════════════════════════════════
  // STAGE 3: THREAD CONTEXT (3 fields)
  // Conversation state and reply obligations
  // ═══════════════════════════════════════════════════════════════

  thread_you_owe: 0|1;             // User owes a reply in this thread
  thread_recency_minutes: number|null;  // Time since last message
  thread_length: number;           // Messages in thread

  // ═══════════════════════════════════════════════════════════════
  // STAGE 4: CONTENT INTENT (4 fields)
  // NLP-lite analysis of email content
  // ═══════════════════════════════════════════════════════════════

  explicit_ask: 0|1;               // Contains question or request
  deadline_epoch: number|null;     // Extracted deadline (chrono-node)
  time_to_deadline_min: number|null;  // Minutes until deadline
  content_intent: 'request'|'inform'|'schedule'|'confirm'|null;

  // ═══════════════════════════════════════════════════════════════
  // STAGE 5: REPLY PREDICTION (2 fields)
  // Heuristic likelihood user needs to reply
  // ═══════════════════════════════════════════════════════════════

  reply_need_prob: number;         // 0.0-1.0 probability
  reply_latency_bucket: number;    // 1=urgent, 2=today, 3=week, 4=someday
}
```

### RFC Gate Implementations

#### NewsletterGate (RFC 2369/2919)

**Purpose**: Detect mailing lists, newsletters, marketing emails

**Detection Strategy** (in confidence priority order):

| Method | Confidence | RFC Standard |
|--------|------------|--------------|
| List-Unsubscribe header | 95% | RFC 2369 |
| List-ID header | 95% | RFC 2919 |
| Campaign headers (X-Mailchimp, X-SendGrid) | 90% | De facto |
| Precedence: bulk/list | 85% | RFC 2076 |
| Newsletter service domains | 85% | Heuristic |
| Sender patterns (no-reply@, newsletter@) | 75% | Heuristic |
| Subject patterns ("[Newsletter]", "Issue #1") | 60% | Heuristic |

**Decision**: confidence ≥ 0.60 → `is_newsletter = 1`

#### AutoGeneratedGate (RFC 3834)

**Purpose**: Detect bounces, out-of-office, system notifications

**Detection Strategy**:

| Method | Confidence | RFC Standard |
|--------|------------|--------------|
| Auto-Submitted header | 100% | RFC 3834 |
| X-Auto-Response-Suppress (Microsoft) | 95% | Exchange |
| Empty Return-Path | 90% | RFC 5321 |
| X-Autoreply/X-Autorespond | 90% | De facto |
| Subject patterns ("Out of Office") | 80% | Heuristic |
| System senders (postmaster@, mailer-daemon@) | 75% | Heuristic |

**Decision**: confidence ≥ 0.65 → `is_auto_generated = 1`

#### CalendarGate (RFC 5545)

**Purpose**: Detect meeting invitations, calendar events

**Detection Strategy**:

| Method | Confidence | RFC Standard |
|--------|------------|--------------|
| Content-Type: text/calendar | 100% | RFC 5545 |
| .ics/.vcs attachments | 95% | RFC 5545 |
| Calendar service domains (zoom.us, calendly.com) | 90% | Heuristic |
| Microsoft Exchange calendar headers | 90% | Exchange |
| Subject patterns ("Invitation:", "Meeting Request") | 85% | Heuristic |
| Meeting link patterns in body | 70-85% | Heuristic |

**Additional Parsing**: Extracts event details (start time, location, organizer) from VCALENDAR

#### OTPGate (RFC 6238 TOTP)

**Purpose**: Detect one-time passwords, 2FA codes, verification emails

**Detection Strategy**:

| Method | Confidence | Notes |
|--------|------------|-------|
| Subject: "Your verification code" + digits | 80% | Common patterns |
| OTP keywords + code patterns | 70-95% | Scaled by count |
| Time-sensitivity indicators ("expires in 10 min") | 75-85% | Urgency signals |
| Service identification (Google, GitHub, etc.) | 70% | Known services |
| Security sender patterns (security@, 2fa@) | 65% | Sender patterns |

**Expiry Detection**: If email age > 15 minutes, mark as expired

### Relationship Scoring

**Purpose**: Calculate sender importance based on interaction history

**Lookback Window**: 6 months (183 days)

**Component Scores** (each 0.0 to 1.0):

```
┌─────────────────────────────────────────────────────────────────┐
│ RELATIONSHIP SCORE COMPONENTS                                   │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│ Reply Frequency (35% weight)                                    │
│ ├── Formula: score = max(0, 1 - (|replyRatio - 0.5| * 2))      │
│ ├── Ideal: 50% reply rate (balanced conversation)              │
│ └── Penalizes: 0% (ignored) or 100% (one-way/spam)             │
│                                                                 │
│ Two-Way Exchanges (25% weight)                                  │
│ ├── Formula: score = min(1.0, exchangeRatio * 2)               │
│ └── Rewards: Genuine back-and-forth conversations               │
│                                                                 │
│ Recency (20% weight)                                            │
│ ├── Formula: score = exp(-daysSinceContact / 90)               │
│ └── 90-day exponential decay (recent contacts score higher)     │
│                                                                 │
│ Email Volume (10% weight)                                       │
│ ├── Sweet spot: 5-50 emails per 6 months                       │
│ ├── Below 5: Linear scale up                                    │
│ ├── Above 50: Penalty (likely newsletter)                       │
│ └── Above 100: Strong penalty                                   │
│                                                                 │
│ VIP Flag (10% weight)                                           │
│ └── User-designated VIP: 1.0, otherwise 0.0                     │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│ Final = (Reply×0.35) + (TwoWay×0.25) + (Recency×0.20)          │
│       + (Volume×0.10) + (VIP×0.10)                              │
│                                                                 │
│ New senders (no history) get neutral baseline: 0.5              │
└─────────────────────────────────────────────────────────────────┘
```

### Content Analysis

**Purpose**: Extract questions, deadlines, urgency, and intent

#### Question Detection

| Type | Pattern | Example |
|------|---------|---------|
| Direct | Ends with `?` | "Can you review this?" |
| Direct | Question words | "What is the timeline?" |
| Implicit | "Please advise/confirm" | "Please let me know" |
| Implicit | "I'd like to know" | "I'd appreciate your input" |
| Implicit | "Wondering if" | "Wondering if you're free" |

#### Deadline Extraction

Uses **chrono-node** date parser with preprocessing:

```
"by today" → "today"
"by tomorrow" → "tomorrow"
"end of week" → "Friday"
"end of day" / "EOD" / "COB" → "today 5pm"
```

Regex patterns: `by|before|until|due|deadline|expires|valid until`

#### Urgency Scoring (0-10 scale)

| Level | Keywords | Points |
|-------|----------|--------|
| Critical | urgent, emergency, critical, ASAP, NOW | +5 |
| High | soon, quickly, prompt, high priority | +3 |
| Medium | timely, follow-up, reminder, pending | +1 |
| Emphasis | Multiple !!!, ALL CAPS in subject | +2 |

#### Intent Classification

```
if (hasDeadline AND urgencyLevel >= 5) → 'confirm'
else if (hasQuestion OR actionItems > 0 OR urgencyLevel >= 5) → 'request'
else if (hasDeadline AND urgencyLevel < 5) → 'schedule'
else → 'inform'
```

## 5. Priority Scoring Algorithm

### 5-Phase Weighted Linear Model

```
┌─────────────────────────────────────────────────────────────────┐
│ PHASE 1: NEGATIVE SIGNALS (reduce score from baseline 50)       │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│ if (is_newsletter)           score += -30   // Newsletter      │
│ if (is_auto_generated)       score += -20   // Auto-generated  │
│ if (otp_detected)            score += -35   // OTP (low value) │
│                                                                 │
│ Rationale: These are typically low-interaction emails that      │
│ shouldn't demand immediate attention.                           │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
                               ↓
┌─────────────────────────────────────────────────────────────────┐
│ PHASE 2: POSITIVE SIGNALS (add bonuses)                         │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│ Relationship:     score += relationship_score × 30  (0-30 pts) │
│ VIP Sender:       score += 15                                   │
│ Explicit Ask:     score += 20                                   │
│ Has Deadline:     score += 15                                   │
│ Urgent Deadline:  score += 25  (if deadline < 24 hours)        │
│ Thread You Owe:   score += 20                                   │
│ Reply Prob:       score += reply_need_prob × 25     (0-25 pts) │
│                                                                 │
│ Rationale: Important relationships, direct requests, and        │
│ time-sensitive items deserve higher priority.                   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
                               ↓
┌─────────────────────────────────────────────────────────────────┐
│ PHASE 3: INTENT MODIFIERS                                       │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│ intent = 'confirm'  → score += 10  // Needs confirmation       │
│ intent = 'request'  → score += 5   // Action request           │
│ intent = 'inform'   → score += -5  // Just informational       │
│ intent = 'schedule' → score += 0   // Neutral                  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
                               ↓
┌─────────────────────────────────────────────────────────────────┐
│ PHASE 4: SPECIAL CASE OVERRIDES                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│ Calendar Invite (event < 24h):                                  │
│   score = max(score, 70)  // Minimum "important"               │
│                                                                 │
│ Security Alert Heuristic (urgent + short deadline + ask):       │
│   score = max(score, 85)  // Near-urgent                       │
│                                                                 │
│ Rationale: Some emails have special handling regardless of      │
│ other features (e.g., upcoming meeting invites).                │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
                               ↓
┌─────────────────────────────────────────────────────────────────┐
│ PHASE 5: FINALIZE & CATEGORIZE                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│ // Clamp to valid range                                         │
│ score = max(0, min(100, score))                                 │
│                                                                 │
│ // Assign category                                              │
│ if (score >= 90) category = 'urgent'     // 🔴 Immediate       │
│ if (score >= 70) category = 'important'  // 🟠 Respond today   │
│ if (score >= 50) category = 'normal'     // 🟢 Standard        │
│ if (score >= 30) category = 'low'        // ⚫ Optional        │
│ else             category = 'spam'       // ⚫ Noise           │
│                                                                 │
│ // Return with explainability                                   │
│ return {                                                        │
│   score: number,           // 0-100                             │
│   category: string,        // Category label                    │
│   confidence: number,      // 0.0-1.0                           │
│   reasoning: string[],     // Human-readable explanations       │
│   feature_weights: object  // Contribution breakdown            │
│ }                                                               │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

```sql
CREATE TABLE emails (
```

```sql
CREATE TABLE ai_cache (
```

## 8. Current Limitations & Known Issues

### Architectural Limitations

1. **No ML Training Loop**: Weights are manually tuned, not learned from user behavior
2. **Single User**: No multi-user support, single database
3. **Gmail-Centric**: IMAP implementation optimized for Gmail
4. **Sequential Feature Extraction**: Not parallelized for batch scoring

### Scoring Limitations

1. **No Semantic Understanding**: Content analysis uses regex, not NLP/LLM
2. **No Thread Context**: Limited thread state tracking
3. **Static Weights**: Weights don't adapt to user preferences
4. **Binary Gates**: Newsletter/auto-generated are all-or-nothing

### Known Edge Cases

1. **New Senders**: Default to 0.5 relationship score (may be too high for cold contacts)
2. **Transactional Emails**: Order confirmations often get low scores (useful vs. noise)
3. **Internal vs External**: No distinction between work domain and external
4. **Language**: English-only pattern matching

### Technical Debt

1. **Legacy TUI**: React-Ink TUI still in codebase but deprecated
2. **AI Manager**: Claude API integration exists but rarely used (heuristics preferred)
3. **Test Coverage**: No integration tests, only unit tests

### Testing Principles

1. **Neutral Baselines**: Use `0` for truly neutral features (not `0.5`)
2. **Boundary Testing**: Test category edges (30, 50, 70, 90)
3. **Pattern Matching**: Use regex assertions for reasoning strings
4. **Explicit Types**: Prevent TypeScript inference errors
5. **Feature Isolation**: Test each gate/analyzer independently
